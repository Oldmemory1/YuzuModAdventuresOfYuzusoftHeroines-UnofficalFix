# 为什么 Wiki 要把数据放进 JSON？

结论先说：**玩家不需要关心 JSON，普通阅读体验也不会因此变复杂。**

把建筑、区划、传统等数据从 HTML 中拆出来，是给 Wiki 的长期维护方式做减负。它让“数据”和“页面长什么样”分开，避免同一个数值在索引卡、详情表、弹窗、说明文字里各写一遍。对于只有十几个条目的静态页面，直接写 HTML 当然也能做；但当内容增长到几十、上百条，并且还在持续移植、修数值、换图标时，散落在页面里的硬编码很快会变成维护负担。

## 直接写进 HTML 看似更省事

例如要记录一个建筑的一级造价，硬编码页面通常会在好几个位置重复出现：

```html
<div class="cost">3,000 合金 · 1,000 心之碎片 · 600 稀有水晶</div>
```

如果索引卡、总表、详情弹窗和统计区又各写一遍，那么以后把 `600` 改成 `650` 时，维护者必须记得修改所有副本。

少改一处，就会出现：

- 卡片显示 600，点开详情却是 650；
- 总览表已经更新，建筑详情仍然使用旧数值；
- 中文页面和搜索摘要不一致；
- 后面新增展示位置时，又复制了一份数据；
- 复查时只能靠肉眼在大量 `div`、`span` 和表格标签里寻找数字。

这类问题的本质不是“数字写错了”，而是同一事实存在多个权威版本。软件工程里通常称为**单一事实来源缺失**。

## 单一事实来源：一个事实只维护一次

现在建筑数据存放在 [`buildings/yuzu_fe_buildings.json`](buildings/yuzu_fe_buildings.json)。每种资源只需要保存一份结构化记录：

```json
{
  "resource": "稀有水晶",
  "amount": 600
}
```

页面只需要根据这条记录生成：

- 建筑索引卡；
- 五级图标；
- 造价栏；
- 建造时间；
- 维护费；
- 产出与岗位；
- 所需科技；
- 点击后的单体详情。

修改 `amount` 后，所有展示位置都从同一处读取，不再需要维护者记住“这个数字在页面里一共出现了多少次”。

当前 Wiki 已经按这个思路拆分了主要数据：

| 内容 | 数据源 | 页面脚本 |
|---|---|---|
| 失落建筑 | [`buildings/yuzu_fe_buildings.json`](buildings/yuzu_fe_buildings.json) | [`buildings/app.js`](buildings/app.js) |
| 特殊星球 | [`districts/yuzu_planet.json`](districts/yuzu_planet.json) | [`districts/app.js`](districts/app.js) |
| 基础区划与 Zone | [`districts/yuzu_districts.json`](districts/yuzu_districts.json) | [`districts/app.js`](districts/app.js) |
| 自定义传统 | [`traditions/traditions.json`](traditions/traditions.json) | [`traditions/app.js`](traditions/app.js) |

HTML 只负责页面骨架和静态说明；CSS 负责外观；JavaScript 负责交互；JSON 负责事实数据。这比把所有内容混在一个 HTML 文件里更容易定位问题和分工。

## 数据、表现和逻辑分离

软件工程里常说的**关注点分离**，落到这个 Wiki 上就是：

### 数据回答“实际是什么”

建筑叫什么、造价多少、维护费多少、提供多少岗位、对应什么科技。

这些内容应该稳定、可列举、可比较，也值得校验。

### 表现回答“怎么显示”

哪一行是紫色、图标放在左边还是右边、窄屏时卡片变成几列。

这些内容主要受浏览器、屏幕尺寸和视觉设计影响。

### 逻辑回答“用户操作后发生什么”

点击某个等级时显示哪一行，关闭弹窗后焦点回到哪里，筛选“科研”时隐藏哪些 Zone。

这些内容属于程序行为，不应该和具体建筑的数值混在一起。

如果三者全部写进 HTML，那么修改一个岗位数字时，维护者要先绕过标签、图标、按钮事件和大量重复内容；修改样式时，又很容易误碰数据。分离之后，每个文件只处理自己的职责，错误范围更小。

## JSON 让修改更容易审查

Git 差异对比对代码维护非常重要。假设把稀有水晶造价从 600 改为 650：

在结构化数据中，差异通常非常明确：

```diff
-    "amount": 600
+    "amount": 650
```

如果数据散落在多个 HTML 表格里，一次提交可能同时包含几十行标签变化，审查者很难快速判断“到底改了数值，还是改了排版”。

多人协作时这个问题更明显：

- 一个人修改建筑数值；
- 一个人调整图标和样式；
- 一个人增加点击详情；
- 一个人补充传统数据。

文件职责分开后，修改不容易互相覆盖，代码审查也更容易聚焦。

## 结构化数据可以被检查

JSON 要求固定的键名、括号和引号。格式写错时，解析器能立即报错，而不是等到页面打开才发现某个卡片消失。

有了稳定结构，还可以自动检查：

- 一座建筑是否恰好有五个等级；
- `id` 是否重复；
- 图片路径是否存在；
- 区划 `resultCode` 是否指向有效结果；
- Zone 的岗位数值是否与脚本一致；
- 传统项目依赖的节点是否都真实存在；
- 数量和统计卡片是否匹配。

例如，本次建筑数据迁移时做过以下校验：

```text
建筑数：12
等级数：60
图片缺失：0
重复 ID：0
脚本与 JSON 名称、描述、科技不一致：0
```

如果所有内容都从 HTML 中反向提取，这类检查会复杂得多，而且容易把排版标签误认为数据。

## 页面可以保持同一个模板

12 条建筑线、60 个等级使用同一套渲染逻辑。新增一条建筑线时，维护者只需要提供数据：

- 建筑 ID；
- 名称和描述；
- 五个等级的图标；
- 造价、维护、产出和效果；
- 科技与研究点数。

页面会自动生成索引卡、等级按钮、详情表和点击行为。不需要复制一整段几百行的 HTML，再逐个修改 ID。

同理，区划页的 15 个 Zone 由同一套卡片和详情弹窗逻辑生成。以后增加“农业 Zone”或修改“物理学研究特化”的岗位数，不需要同时寻找十几个散落在页面中的数字。

## 为什么区划要拆成两个 JSON？

特殊星球和区划不是同一种实体：

- 星球描述星球职业、区划集合和殖民条件；
- 区划描述造价、维护、Zone 槽、岗位和解锁条件。

拆成 [`yuzu_planet.json`](districts/yuzu_planet.json) 和 [`yuzu_districts.json`](districts/yuzu_districts.json) 后，修改“夕阳之城的人口承载”不会碰到“梦境矿区提供多少岗位”，审查和冲突范围更小。

不过拆得太细也会增加理解成本。判断是否继续拆分时，可以看两个对象是否经常一起变化、是否有独立含义、是否能通过 ID 清晰引用。并非每个字段都值得单独开一个文件。

## 为什么不直接使用 JavaScript 数据文件？

浏览器的 JavaScript 确实可以直接保存对象，但纯数据文件用 JSON 有几个优势：

- 格式更严格，不容易混入函数、计算表达式或临时变量；
- 可以被其他脚本、编辑器、校验器直接读取；
- 更容易导出给表格、数据库或未来的 Wiki 工具；
- 数据文件中不会出现“顺便做一点页面逻辑”的情况。

当前目录里的 `data.js` 只是浏览器本地打开页面时使用的兼容包装。它由 JSON 自动生成，不应手动修改：

```text
yuzu_fe_buildings.json  ──构建脚本──>  data.js  ──> app.js 渲染页面
yuzu_planet.json        ──┐
yuzu_districts.json     ──┴─构建脚本──> data.js ──> app.js 渲染页面
```

之所以需要这一步，是因为直接用 `file://` 打开 HTML 时，浏览器通常会限制 `fetch()` 读取本地 JSON。生成后的 `data.js` 可以被普通 `<script>` 标签加载，从而保留“双击 HTML 就能看 Wiki”的体验。

## 这不是为了强迫玩家学技术

普通玩家的使用方式没有任何变化：

1. 双击或通过 Wiki 入口打开页面；
2. 查看建筑、区划和传统；
3. 点击图标打开该等级的详情。

玩家不需要安装 Node.js，也不需要编辑 JSON。

JSON 是维护者修改数据的入口，不是玩家阅读 Wiki 的前置条件。

## 代价是什么？

这种方案也不是零成本：

- 修改 JSON 后需要运行一次构建脚本生成 `data.js`；
- JSON 不接受注释，字段名必须严格一致；
- 数据结构变化时，渲染脚本可能需要同步调整；
- 对只有三五行、永远不修改的纯文字页面，拆成 JSON 可能反而过度设计。

所以这里采用 JSON，不是因为“JSON 天然高级”，而是因为当前 Wiki 已经具备以下特点：

- 条目数量多；
- 同一数据需要在多个视图中出现；
- 会随着 Mod 移植持续修改；
- 需要图片、分类、层级、依赖和点击详情；
- 需要自动校验和多人协作。

在这种规模下，结构化数据带来的可维护性收益明显高于一次性搭建成本。

## 维护者应该修改哪个文件？

| 要修改的内容 | 应修改 |
|---|---|
| 建筑造价、岗位、科技、描述 | 对应的建筑 JSON |
| 特殊星球数值和说明 | `yuzu_planet.json` |
| 基础区划、Zone、岗位数值 | `yuzu_districts.json` |
| 传统项目、依赖、效果 | `traditions.json` |
| 页面布局和视觉样式 | `style.css` |
| 点击、筛选、弹窗行为 | `app.js` |
| 本地直接打开所需的包装 | 通过脚本生成 `data.js`，不要手动编辑 |

生成命令：

```bash
.venv/bin/python scripts/build_buildings_wiki_data.py
.venv/bin/python scripts/build_districts_wiki_data.py
.venv/bin/python scripts/build_traditions_wiki_data.py
```

如果项目使用 `uv`，也可以把命令中的 `.venv/bin/python` 换成 `uv run python`。

## 一句话总结

把 Wiki 数据放进 JSON，不是把页面做复杂，而是把“同一事实维护很多遍”的复杂性提前消掉。它用一次结构化的成本，换取后续修改、校验、协作和扩展时的稳定；玩家看到的仍然是一个普通、可以直接打开的浅色 Wiki 页面。
